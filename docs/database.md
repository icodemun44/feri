# Database and migrations

Prisma is the **single source of truth** for the schema. Supabase is used for Auth and Storage; the `supabase/migrations` folder is intentionally unused.

## Conventions

- Table names are plural snake_case (`seller_applications`); column names are snake_case. Prisma models use PascalCase and camelCase with `@map` and `@@map`.
- Primary keys are UUIDs generated by the database (`gen_random_uuid()`), so raw SQL inserts work too.
- Every timestamp is `timestamptz`. Every table has `created_at`; mutable tables also have `updated_at`.
- Money is an integer number of paisa (`price_minor`, `total_minor`).
- Statuses are Postgres enums. Adding an enum value is a safe migration.
- Anything that is an audit or history value that changes often (for example audit actions) is a plain string, so it never needs a migration.

## Tables

`users`, `user_profiles`, `categories`, `seller_applications`, `sellers`, `products`, `product_images`, `cart_items`, `orders`, `order_items`, `payments`, `reviews`, `banners`, `audit_logs`.

Key relationships:

- A user has one profile, at most one seller profile, many seller applications, many orders, many reviews.
- A seller application that is approved produces exactly one seller.
- A product belongs to one seller and one category and has ordered images. It has a `status` (draft, active, sold, removed) and a separate `review_status` (pending or approved) that records whether an admin has checked it.
- Orders record who cancelled and why in `cancellation_reason` (empty when the buyer cancels).
- A cart item links one user to one product (unique together).
- An order belongs to one buyer and **one seller**, has many items and one payment.
- A review belongs to exactly one order item.

## Rules enforced by the database

These are in `prisma/migrations/*_constraints_and_rls/migration.sql` because Prisma cannot express them:

- One open (pending or in review) seller application per applicant (partial unique index).
- Non-negative prices, quantities and totals; ratings between 1 and 5; banner start before end; lowercase emails.
- Order numbers start at 10001.
- Row Level Security is enabled on every table with no policies, and table privileges are revoked from Supabase's `anon` and `authenticated` roles. The app talks to the database only through Prisma on the server (the table owner), so the public Data API exposes nothing.

## Migration workflow

| Task                               | Command                               |
| ---------------------------------- | ------------------------------------- |
| Create and apply a migration (dev) | `pnpm db:migrate --name <short_name>` |
| Apply migrations (CI, production)  | `pnpm db:deploy`                      |
| Check migration state              | `pnpm db:status`                      |
| Start over locally                 | `pnpm db:reset`, then `pnpm db:seed`  |
| Regenerate the client              | `pnpm db:generate`                    |

Rules that prevent migration trouble:

1. **Never edit a migration that has been merged.** Write a new one.
2. One logical change per migration, with a clear name.
3. Destructive changes (drop column or table, type change) use two steps across two releases: add the new thing and move the data, then remove the old thing.
4. A new required column on a table with data needs a default or a backfill in the same migration.
5. Raw SQL that Prisma cannot model goes in its own migration. Create the folder `prisma/migrations/<timestamp>_<name>/migration.sql` by hand and run `pnpm db:migrate`.
6. CI applies every migration to an empty database and then runs `prisma migrate diff ... --exit-code`. If the schema file and the migrations disagree, the build fails.
7. Deploys run `migrate deploy` before the new app version starts (Docker Compose does this with the `migrate` service).

## Connections

- `DATABASE_URL`: used by the app at runtime. In production use the pooled connection string.
- `DIRECT_URL`: used by `prisma migrate`. Must be a direct (non-pooled) connection.
- Locally both point at `postgresql://postgres:postgres@127.0.0.1:54322/postgres`.

## Seeding

- `pnpm db:seed` creates the five categories and three banners. It is safe to run repeatedly.
- `pnpm demo:seed` (local Supabase only) creates demo accounts and 12 products. Accounts: `admin@feri.test`, `seller@feri.test`, `buyer@feri.test`, password `Password123!`.
- `pnpm admin:create -- --email you@example.com --password '...' --name 'Your Name'` creates or promotes a real admin.
